Create the most performant megakernel for one Kimi K3 text decode step using CUDA C++ and inline PTX, on one GB300 NVL72 tray of 4 NVIDIA GB300 GPUs (B300 silicon, sm_103a; check with nvidia-smi in a gpu-run request). Tensor parallel 4: each rank runs exactly one persistent kernel launch per step, and that launch includes all communication between ranks. The model has 93 layers: KDA (Kimi delta attention) layers, gated MLA layers at 3, 7, ..., 91 and 92, a latent MoE with 896 MXFP4 experts and top-16 routing, and block attention residuals. The graded cases of this run are the synthetic 8-layer TP4 cases kimi-k3-syn-l8-tp4-b1-s8192, kimi-k3-syn-l8-tp4-b8-s8192 and kimi-k3-syn-l8-tp4-b64-s8192. The real-weight TP8 cases in TASK.md need 8 GPUs on one node, which this tray does not have, and there is no checkpoint at /weights: do not run them. You can spawn parallel Sonnet subagents for the implementation, but you own the integration and the correctness.

Define a correctness check for the megakernel against eager PyTorch that is flexible enough to let you make optimizations: for example, a tolerance relative to the error of the BF16 eager model against an FP32 run, not bit-exact agreement. Refer to the model structure on Hugging Face (moonshotai/Kimi-K3, including its modeling code) as needed, and download whatever else you need (see ENVIRONMENT.md). Run your check on fresh synthetic weights (the oracle in reference/megabench/tasks/kimi.py makes them with kimi.synthetic_weights) on the graded cases and on the development cases. Describe the check in /work/CORRECTNESS.md, implement it as a script in /work, and run it on every change you keep.

The harness interface, the cases and the benchmark's own correctness band are in TASK.md. ./check_candidate --case ID runs the launch audit, that correctness band and the timing, and it must pass on every graded case. ./sol_info --case ID --json gives the per-GPU HBM floor, and ./profile_candidate --case ID runs Nsight Compute. If BASELINES.json is present, it has the vLLM latency for the real-weight cases; there is no vLLM baseline for the synthetic cases. GPU jobs go through gpu-run, and a 4-GPU request waits for a whole tray, so batch your experiments.

Keep /work/PROGRESS.md up to date: for each attempt, the idea, the latencies before and after, kept or reverted, and why. Commit each kept change with its measured latencies.

The goal is met when the committed megakernel passes your correctness check and ./check_candidate on every graded case on a fresh run, and either its warm CUDA-event latency is at most 1.4x the ./sol_info HBM floor on every graded case, or five consecutive optimization attempts each improved latency by less than 2%. Record the final latency of each graded case, its ratio to the floor and the commit hash in PROGRESS.md.
