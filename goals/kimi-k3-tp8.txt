Create the most performant megakernel for one Kimi K3 text decode step using CUDA C++ and inline PTX, on one node of 8 NVIDIA B300 GPUs (sm_103a; check with nvidia-smi in a gpu-run request). Tensor parallel 8: each rank runs exactly one persistent kernel launch per step, and that launch includes all communication between ranks. The model has 93 layers: KDA (Kimi delta attention) layers, gated MLA layers at 3, 7, ..., 91 and 92, a latent MoE with 896 MXFP4 experts and top-16 routing, and block attention residuals. You can spawn parallel Sonnet subagents for the implementation, but you own the integration and the correctness.

Define a correctness check for the megakernel against eager PyTorch that is flexible enough to let you make optimizations: for example, a tolerance relative to the error of the BF16 eager model against an FP32 run, not bit-exact agreement. Refer to the model structure on Hugging Face (moonshotai/Kimi-K3, including its modeling code) as needed, and download whatever else you need (see ENVIRONMENT.md). The real checkpoint is already on the node: GPU jobs (gpu-run) see it read-only at /weights, in the per-rank layout that reference/megabench/tasks/kimi_checkpoint.py describes (load it with kimi.checkpoint_weights). Do not download the weights again. Run your check on the real weights. Describe the check in /work/CORRECTNESS.md, implement it as a script in /work, and run it on every change you keep.

The harness interface, the cases and the benchmark's own correctness band are in TASK.md. ./check_candidate --case ID runs the launch audit, that correctness band and the timing, and it must pass on every graded case. Each real-weight check loads about 200 GB per GPU, so do most iterations on the synthetic and development cases. ./sol_info --case ID --json gives the per-GPU HBM floor, ./profile_candidate --case ID runs Nsight Compute, and BASELINES.json has the vLLM latency for each graded case. GPU jobs go through gpu-run, and an 8-GPU request waits for a whole node, so batch your experiments.

Keep /work/PROGRESS.md up to date: for each attempt, the idea, the latencies before and after, kept or reverted, and why. Commit each kept change with its measured latencies.

The goal is met when the committed megakernel passes your correctness check on the real weights and ./check_candidate on every graded case on a fresh run, and either its warm CUDA-event latency is at most 1.4x the ./sol_info HBM floor on every graded case, or five consecutive optimization attempts each improved latency by less than 2%. Record the final latency of each graded case, its ratio to the floor, its speedup over BASELINES.json and the commit hash in PROGRESS.md.
