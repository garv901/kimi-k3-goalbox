# Negative controls for the evaluator (prepared 2026-11-12; CPU review, Step 6 on one GPU, Step 7 on four GPUs the same day)

Every GB300 run so far (Steps 1 to 5) used the oracle itself as the candidate and showed the evaluator *accepting* a correct candidate. These three submissions show it *rejecting* an incorrect one, each through exactly one check. They wrap the unmodified oracle; the oracle, grader, launch audit, benchmark methodology and the positive control are unchanged (no file under `megabench/`, `setup/` or `sandbox/` differs from commit `52f8d8c`).

| File | What it corrupts | Exact mechanism | Expected failure (status `incorrect`, AssertionError) |
|---|---|---|---|
| `positive_control_oracle.py` | nothing | `build()` returns `kimi.reference`; byte-identical to the Step 1 to 5 candidate, sha256 `6f9e8a84…c906` | none: passes; `non_megakernel` on a GPU, `correctness_only` on CPU |
| `negctrl_logits.py` | logits, row 0 | on each rank's own vocabulary shard: `delta = 1.0 * rms(logits[0])`, then `logits[0, ::4] += delta` (every 4th index, one quarter of the row). Deterministic, finite; shapes and dtypes unchanged; every other output is the oracle's | `logits: {'candidate_rel_l2_max': ≈0.50, 'oracle_rel_l2_max': ≈0.05, 'worst_ratio': ≈5}` from the FP32 band check, row 0 only; next_token, routing, states, cache_length pass |
| `negctrl_routing.py` | expert_ids, layer 1 (first MoE layer), row 0, slot 0 | run the oracle; take its sorted top-k set of that row; replace its lowest id with the smallest expert id not in the set; rerun the same BF16 oracle **forced onto the corrupted routes** and return that output (so logits, next_token, states are consistent with the corrupted routes and the band passes); read the forced run's `route_shortfall` for the replacement; abort with RuntimeError (status `error`, documented) if it is below 0.05, i.e. a near-tie | `expert_ids: {'candidate_max_shortfall': 0.2 to 0.6, 'oracle_max_shortfall': …, 'allowed': ≈0.002 to 0.019, 'sets_differing_from_oracle': 1}` from the near-top-k routing rule |
| `negctrl_immutability.py` | input `l3_kv_cache` (first MLA layer's latent cache), element `[0, 0, 0]` | after the oracle step has produced its outputs: `inputs['l3_kv_cache'][0, 0, 0] += 1.0` (BF16, standard-normal data, so the bits always change). Outputs are bit-identical to the oracle's | `candidate mutated input l3_kv_cache` from `check_unchanged()`, which runs before `compare()`; AssertionError, so `incorrect`, not `error` |

Why the routing control reruns the oracle on the corrupted routes: `compare()` grades the continuous outputs against an FP32 reference run on the *candidate's* routes. A candidate that returned the oracle's logits with only `expert_ids` edited would also fail the logits band (its logits belong to other routes), and the failure would not be attributable to the routing check alone.

Why `l3_kv_cache`: `snapshot()` copies tensors of at most 64 MB to the host and compares exactly; larger tensors get two 64-bit device checksums. `l3_kv_cache` is `[B, 8192, 512]` BF16: 8 MB at batch 1, 64 MB at batch 8 (the host-copy limit itself) and 512 MB at batch 64 (checksum path). The dev TP1 case and a later TP4 B64 replication would exercise both paths. The cache is replicated on all ranks, so every rank's own check must fail.

## Record file

The evaluator discards the candidate's stdout and stderr (ISSUES.md item 9). With `GOALBOX_NEGCTRL_RECORD=<path>` set, each control appends one JSON line per `run()` call to `<path>.rank<N>.jsonl` (rank from `case['execution']`, 0 on a single GPU): the logits control records row, stride, number of perturbed indices, `delta` and the relative L2 change of the row on that shard; the routing control records layer, row, slot, original and replacement expert ids, the replacement's shortfall below the k-th best score, the largest shortfall in the other rows (expected 0) and in later layers of the same row; the immutability control records tensor, index, value before and after, byte size and which snapshot path applies. Without the variable nothing is written.

## Side effects reviewed

- Logits and routing controls do not touch the inputs (their failures come from `compare()`, after `check_unchanged()` passed: verified by the CPU review). The immutability control's outputs are bit-identical to the oracle's (verified).
- The routing control calls the oracle twice per `run()` and the forced pass issues the same collectives as a normal step, in the same order on every rank (the routes are identical on all ranks, as the grader's own checksum requires). The near-tie abort happens after the forced pass completed, so it cannot leave ranks waiting in a collective; `agree()` then reports it.
- The immutability control's mutation accumulates by +1.0 per call on one element of the perf inputs during timing and the audit; harmless and outside correctness.
- Timing and launch counts of the controls are meaningless (the routing control doubles the work) and must not be compared with Steps 1 to 5.
- In the single-GPU path, `check_trials()` raises at the first failing trial and `evaluate_case()` stops there, so a negative-control run produces no timing or audit section; the status comes from `_worker()`'s mapping (AssertionError to `incorrect`, anything else to `error`).

## CPU review (`cpu_review_driver.sh` → `cpu-review-<ts>/`)

`cpu_review.py` loads each file with the evaluator's own `_load_submission()` (tiny contract, the real dev-case contract, and with the distributed `execution` key), runs the evaluator's own `check_trials()` and the per-trial sequence `snapshot → reference → candidate → check_unchanged → compare` on five fixed seeds, on a tiny Kimi geometry (5 layers, 128 experts, top-8, batch 3) on the CPU. `cpu_review_driver.sh` adds `py_compile`, versions, and four real-geometry runs of the actual CLI (`megabench evaluate --device cpu`, case `kimi-k3-dev-l4-tp1-b8-s8192`, 1 trial) with the record file enabled. No GPU is visible to any of it. Results (two runs, `cpu-review-20261112T132304Z` and `cpu-review-20261112T133917Z`, rack 3 tray09, no GPU process):
- Tiny geometry, fixed seeds: 5 of 5 as expected for every control in both runs (positive control ratios 0.39 to 0.49; logits control rel-L2 0.50, ratios 3.6 to 18.7; routing control shortfall 0.20 to 0.61 against allowances 0.001 to 0.016; immutability control `candidate mutated input l3_kv_cache` with oracle-identical outputs).
- Tiny geometry, `check_trials()` with its own random seeds: positive pass, logits and immutability rejected as expected in both runs; the routing control hit its documented near-tie abort in both runs (`RuntimeError: negative control inconclusive: replacement expert 1 is within 0.0291 of the k-th best score`, status would be `error`). With 128 experts and top-8 the smallest id outside the set is often a near-tie; the first run's `cpu_review.py` did not yet count that documented outcome as expected (`ALL EXPECTATIONS MET: False`), the second run's does. The abort is the designed, visible alternative to a silent pass; a GPU run that hits it is reported as inconclusive and rerun, not counted as a rejection.
- Real geometry (`kimi-k3-dev-l4-tp1-b8-s8192` on CPU, 1 trial, about 3 minutes and 63 GB RSS per negative control, 6 minutes for the positive control), identical outcome in both runs: logits `incorrect`, `logits: {'candidate_rel_l2_max': 0.5002, 'oracle_rel_l2_max': 0.029, 'worst_ratio': 14.6 / 14.8}`; routing `incorrect`, `expert_ids: {'candidate_max_shortfall': 0.711 / 0.535, 'allowed': 0.0070 / 0.0049, 'sets_differing_from_oracle': 1}` (record: layer 1, row 0, original expert 30 / 2 replaced by 0, other rows 0.0); immutability `incorrect`, `candidate mutated input l3_kv_cache` (64 MB tensor, host-copy path); positive control `correctness_only`, correctness `pass`. The three failure records carry no `submission_sha256` (ISSUES.md item 11); the exit code is 1 for all four, including the passing positive control, because only `ok_provisional` counts as passed (ISSUES.md item 8).

Rank-local limitation (details in the report): the evaluator grades routes and outputs as one TP group (route checksums all-reduced before the forced references, band sums all-reduced), so a corruption on one rank produces the same error on every rank and never reaches the near-top-k rule; only a rank's own local error (candidate exception, failed `check_unchanged()`) is attributed with a "rank N:" prefix. A forced rerun on one rank would be a collective mismatch and was not written. Two setup mistakes of the preflight itself (an invalid tiny geometry: `intermediate/tp` must be a multiple of 32 for the MXFP4 shards; a missing `--session-id` in the CLI command) were fixed before the committed run; the two aborted directories were removed.
