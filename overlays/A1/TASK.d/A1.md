# A1: measurement tools for multi-rank kernels

Three extra tools sit in the workspace root. Each writes its output under `reports/`, and each
uses GPUs only through `./gpu_run`. Run any of them with `--help` to see all options.

## `./flag_audit`: check which experiment code the shipped build compiles in (no GPU, takes seconds)
- **When to run it:** before every `./check_candidate` you plan to keep, and after you revert or
  abandon an idea.
- **What it does:** lists every `#if/#ifdef/#ifndef` switch in the sources your build compiles. For
  each one it shows the state in the **shipped** build. The tool reads the nvcc flags from your
  Python build code. For an env var used in the nvcc command, it uses the default value, because
  the grader does not set your env vars.
- **When it fails:** it exits 1 when a block that NOTES.md calls "no gain", "slower", "reverted",
  "off" or similar is still compiled in. To fix it, delete the dead path or change the build's
  default flags.
- **If the match is wrong:** say so in NOTES.md.
- **Other modes:** `./flag_audit --flags "-DFOO"` audits as if the build used those flags, and
  `--all` lists include guards and platform checks too.

## `./phase_table`: time per phase, per block and per rank (all GPUs, one run of about 2 to 4 min)
Use it to find which phase, block or rank is on the critical path before and after a change. The
stamps add a timer read and a few stores per barrier (about 1 to 2%), so confirm every speedup with
`./check_candidate`.

1. Add `#include "phase_table.cuh"` to the .cu file that defines the kernel. The header compiles
   to nothing unless you build with `-DPHASE_TABLE`, so the stamps can stay in the scored build.
2. Add `PT_INIT();` as the kernel's first statement and `PT_FINISH();` as its last.
3. In your grid barrier, record the arrival and the release, in the thread that waits. Pass a
   call-site id down to the barrier, for example `#define GSYNC(c) grid_sync(bar, __LINE__)`:
   ```cuda
   __device__ void grid_sync(unsigned* bar, int site) {
     __syncthreads();
     if (threadIdx.x == 0) { PT_ARRIVE(site); /* arrive + spin */ PT_RELEASE(site); }
     __syncthreads();
   }
   ```
   For a cross-GPU barrier, give each internal step its own id, for example `site | 0x10000`.
   A phase is the interval between two consecutive barriers, and the table names it after the
   barrier that closes it.
4. Optional extras:
   - `PHASE_BEGIN(id)` / `PHASE_END(id)` time a sub-phase.
   - `PT_MARK(id)` sets the context, for example the layer index.
   - `PT_SPIN(while (flag < n) {});` counts time spent waiting on counters.
   - Only thread 0 of each block writes stamps. Any other thread's stamps are ignored.
5. In `PYBIND11_MODULE`, add `PHASE_TABLE_PYBIND(m);`. This exposes
   `phase_table_bind(ptr, words)`.
6. In `submission.py`, export `build_timeline(case)`. This is the same contract that
   `./timeline_candidate` uses:
   ```python
   def build_timeline(case):
       os.environ['MK_FLAGS'] = os.environ.get('MK_FLAGS', '<your default flags>') + ' -DPHASE_TABLE'
       runner = build(case)       # must build/load a SEPARATE extension for these flags
       ext, dev, nblocks = ...    # your loaded extension module, device, and grid size
       slots = 2048               # >= barrier crossings + marks + sub-phase stamps per block per launch
       buf = torch.zeros(16 + nblocks * (8 + 4 * slots), dtype=torch.int64, device=dev)
       assert ext.phase_table_bind(buf.data_ptr(), buf.numel()) == 0   # -1: built without -DPHASE_TABLE
       names = {}                 # optional {id: label}; else ./phase_table --src FILE labels line ids
       def run(inputs):
           runner(inputs)
           return buf
       return run, names
   ```
   The instrumented build needs its own extension or cache key. Make sure your build cache key
   includes the flags. Build it once before you run the tool, for example with
   `MK_FLAGS="... -DPHASE_TABLE" python3 -c "import <your host module>; <load>()"`. That way it
   does not compile while the run holds all the GPUs.

**How to run it:**
- `./phase_table` uses the raw scenario (`--trial 0`) by default.
- `--trial 1` selects full acceptance, and `--launches 3` averages three launches.
- `--src mk.cu` labels ids that are line numbers with the nearest `// ===` comment or function.
- `--group attn='attention'` prints the share of the span taken by phases whose label matches
  the regex.
- `--analyze reports/phase_table-ID` re-runs the analysis without the GPU.

**How to read the table** (µs per launch, summed over each phase's occurrences, sorted by wall):

| Column | Meaning |
|---|---|
| `wall` | release-to-release time of the phase; this is its time on the critical path |
| `share` | `wall` divided by the in-device span |
| `bmax` / `bmean` | per-block busy time (slowest and mean), from that block's previous release to its arrival |
| `skew` | `bmax − bmean`, the intra-GPU imbalance |
| `bar` | time from the last arrival to the release |
| `wait` | mean time a block waits at the barrier |
| `rskew` | max over ranks minus the mean of `bmax`, the cross-rank imbalance |
| `xsprd` | mean over ranks of wall minus the fastest rank's wall: slow ranks show it on work phases, fast ranks on the phase that waits for peers |
| `slow r` | the rank that is usually the slowest |

Below the table:
- **Critical path:** each rank's span split into work + skew + sync + tail. A block that waits
  for peer ranks counts as busy, so cross-rank waits show up as skew; use `rskew`/`xsprd`.
- **Contexts and sub-phases:** wall time per context and per sub-phase.
- **summary.json:** everything above, written to `reports/phase_table-*/`.

## `./profile_candidate_all_ranks`: Nsight Compute on every rank (all GPUs; about 1.5 min per replay pass)
- **Why not plain ncu:** ncu's default kernel replay hangs or fails on a kernel that waits for peer
  ranks, and a single ncu over all ranks deadlocks, because ncu profiles one kernel at a time.
  This tool runs one ncu per rank with `--replay-mode application --target-processes all`.
  Every replay pass re-runs each rank with a fresh rendezvous, and only the warmed launch is
  profiled (the same window `./profile_candidate` uses).
- **Default run:** `./profile_candidate_all_ranks` takes 1 pass. It reports per rank the DRAM bytes
  read and written, the duration, and instruction counts (total and tensor/tc pipes).
- **Other sets:**
  - `--set l2` adds the L2 hit rate (3 passes).
  - `--set pipes` gives alu/fma/lsu/tensor pipe counts (about 3 passes).
  - `--set stalls` samples warp stall reasons (2 passes).
  - `--metrics a,b` takes your own metric list; each extra pass costs a full run.
  - `--kernel regex:NAME` restricts profiling to one kernel.
  - `--timeout S` sets the hard timeout in seconds (default 900).
- **Reading it:** under ncu the ranks start at different times, and the early ranks spin on peer
  flags. DRAM bytes and tensor-pipe counts are valid. Duration, percentages and the total
  instruction count include that spin, so trust them only on the rank with the shortest duration.
  Compare bytes between builds, and use `./phase_table` for time.
- **Output:** `reports/ncu_all_ranks-*/` holds `table.txt`, `summary.json`, `prof_r<rank>.ncu-rep`
  and the per-rank logs. `--import DIR` re-prints a finished report.
