# A3: parallel phase engines (capture → task_ab → engine subagents → merge)

This workspace lets you improve several phases of the kernel at the same time, each on ONE GPU,
instead of one serial loop on all GPUs. You are the **integrator**: you profile, define the phase
contracts, run up to 3 `engine` subagents in parallel, and merge their results one at a time.

Tools (all GPU work goes through `./gpu_run`; these call it for you):
- `./capture` — runs your kernel on all ranks (lease of all GPUs) with capture points enabled and saves
  each phase's inputs/outputs for the chosen layers to `reports/capture-<stamp>/`.
- `./task_ab A_DIR [B_DIR] --task T --in IN --out OUT --layer L` — restores the captured state of
  one rank on ONE GPU (1-GPU lease), launches the standalone phase kernel `T`, checks every region
  of record `OUT` against the capture (case tolerances: float rel-L2 ≤ rtol (bf16: bf16_rtol) and
  max-abs ≤ atol + rtol·max|golden|; integers exact), and times A and B alternately with CUDA events
  (cold L2, ≥ 5 reps; default 9). Prints PASS/FAIL per side and a verdict (B FASTER / SLOWER / SAME
  within noise). `--rank all` replays every rank; `--flags-a=... / --flags-b=...` add nvcc flags.
- `./task_ab --selftest` — 1-GPU self-test on a toy kernel (`a3tools/toy/`, also the example of
  everything below).
- `phases.template.md` — the contract table; example filled for the toy in `a3tools/toy/phases.md`.
- `.claude/agents/engine.md` — the `engine` subagent.

## One-time setup: make the kernel capturable (≈ 30 min, do it once, keep it in the tree)
All of this compiles to nothing in the normal build.
1. `#include "ss_task.cuh"` in the kernel source after your parameter struct is defined
   (the header documents the macros). Make sure a changed header triggers a rebuild.
2. At the top of the persistent kernel: `SS_CAP_PARAMS(&p, sizeof(p));` (records the launch's
   parameter block; task_ab re-points every pointer in it to the restored buffers on one GPU).
3. At each phase boundary you want to work on, right after the grid barrier / sync:
   `SS_CAP("name_in", layer, SS_REG("buf", ptr, count, SS_BF16), ...)` and the same after the phase
   with its outputs (`"name_out"`). Register everything the phase reads that changes during the
   launch (scratch buffers, comm buffers incl. peers' if it reads them, output tensors) — it is
   simplest to register the whole scratch buffer at the `_in` point and the typed outputs at the
   `_out` point. Read-only inputs (weights, caches) need not be registered: task_ab regenerates them
   from the case's seed. Memory not registered is restored from its end-of-launch contents.
   SS_CAP is grid-collective (all blocks must reach it); it only acts on the armed launch for the
   selected layers, so it never deadlocks other paths.
4. Move the phase's code into a `__device__` function that the persistent kernel calls, and add a
   standalone entry point:
   ```
   #ifdef SS_TASK
   __global__ void __launch_bounds__(NT, 1) task_X(const __grid_constant__ KP p) {
     /* same context setup as the persistent kernel (pointers, rank, ...) */
     X(ctx, ..., ss_task_layer());             // ss_task_aux() carries --aux (e.g. a draft flag)
   }
   SS_TASK_REGISTER(X, task_X, KP, NT, DYN_SMEM_BYTES)
   #endif
   ```
   State that lives only in registers or shared memory at the boundary (counters, routing tables,
   epochs) is not captured: recompute it inside the task, or write it to a buffer you register.
5. `ss_task.py` in the candidate directory: `build_ext(flags) -> path of the built .so`, building the
   same source with your default flags plus `flags` (e.g. set the env var your build reads and call
   your loader). Optional hooks: `make_inputs(case, seed, trial, device, rank)`,
   `build_runner(case, rank, world, group, device)`, `case()` (defaults: the workspace's benchmark
   case via `reference/` and `submission.build`).
6. `./capture --layers L1,L2` (pick layers that cover the different layer kinds), then check one phase:
   `./task_ab . --task X --in X_in --out X_out --layer L1` must PASS bit-exact or within tolerance,
   and its time should be close to the phase's in-kernel window (`./phase_table`); note both in
   `phases.md`. If the standalone time is far from the in-kernel window, say so in the row — gains
   measured on that phase are less trustworthy.

## Integrator loop
1. **Profile** the current candidate (`./phase_table`, `./check_candidate`). Rank phases by
   critical-path time and by distance from their hardware floor.
2. **Fill `phases.md`** (from `phases.template.md`) for the phases you will hand out: inputs/outputs
   with layouts, resource budget, sync in/out, in-kernel window, task_ab time. Commit it.
3. **Launch up to 3 `engine` subagents IN PARALLEL** — several Task tool calls in ONE message — each
   on a different, independent phase (no shared output buffers, no shared budget you can't split).
   Give each: phase, its contract row, the `./task_ab` arguments and capture dir, a variant name.
   While they run, you may do other non-GPU work or one more 1-GPU job; you must not change files
   they depend on (the contract, the capture, the parent sources).
4. **Merge one diff at a time** into the main tree, in order of expected gain: apply, build,
   `./check_candidate`. Keep it only if it passes and the score improves beyond the check's noise;
   otherwise revert it and note why (gains that do not show up end-to-end are usually hidden behind
   another phase's wait or a barrier — check `./phase_table`). Record each in the merge log.
5. After merges that change layouts or the phase code paths, re-run `./capture` before the next
   engine round so goldens match the new tree. Update `phases.md`, then repeat from 1.

Keep the main tree passing `./check_candidate` at all times; engines never run it.
