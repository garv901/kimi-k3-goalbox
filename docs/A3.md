# A3 overlay: parallel phase engines (capture, task_ab, engine subagent)

Owner: builder-a3. Files: `overlays/A3/`, `arms/A3.toml` (overlays `["A1","A3"]`), this doc,
`docs/A3_fixture/` (verification fixture, NOT copied into workspaces).

## What ships in a workspace (overlays/A3/)
| path | what |
|---|---|
| `ss_task.cuh` | header the agent includes in its kernel: `SS_CAP_PARAMS`, `SS_CAP(name, layer, SS_REG(...)...)` capture points, `SS_TASK_REGISTER` standalone entry points; compiles to nothing unless `-DSS_CAPTURE` / `-DSS_TASK` |
| `./capture` | `./gpu_run -g 8` torchrun of the candidate's `-DSS_CAPTURE` build; arms capture on launch 1 (after a warm-up), saves records of the chosen layers on every rank to `reports/capture-<stamp>/` (`manifest.json` + `rank<r>.pt`) |
| `./task_ab` | `./gpu_run -g 1`: restores one rank's state at record `--in` on one GPU, launches registered task `--task` of variant A (and B), checks record `--out` against the capture with the case tolerances, times A/B alternately (CUDA events, cold L2, default 2 warm-up + 9 reps), prints PASS/FAIL + verdict, writes `reports/task_ab-*/result.json` |
| `./task_ab --selftest` | toy kernel (`a3tools/toy/`) capture + A/B against a deliberately slowed variant; exit 0 iff both PASS and the verdict is `B SLOWER` |
| `phases.template.md` | contract table template; `a3tools/toy/phases.md` is the filled toy example |
| `.claude/agents/engine.md` | `engine` subagent: one phase, `variants/<phase>/<name>/`, iterates with `./task_ab` (1 GPU), returns best diff + numbers |
| `TASK.d/A3.md` | integrator workflow (instrument once → profile → fill phases.md → ≤ 3 engines in parallel → merge one at a time → `./check_candidate`) |

## Design (why this approach)
Capture approach: **(b) a debug build of the kernel that writes buffers at phase boundaries**, not the
Python reference: the golden data must be what the kernel phase consumes and produces in the
kernel's own layouts (fp32 split-K accumulators, padded/qdq'd copies, pair lists ...), which the
eager reference does not have.

- **Capture points** are grid-collective device calls (own grid barrier, copy with `ld.cg`, barrier)
  that act only on the armed launch and selected layers, so the normal build and non-selected layers
  are untouched. The parameter block of the launch is recorded too (`SS_CAP_PARAMS`).
- **Restore without candidate host code.** task_ab never runs the candidate's host runner (it needs
  8 ranks + IPC). It re-points every 8-byte word of the captured parameter block: words inside an
  input tensor → the regenerated input (same seed/trial/rank via the case's `make_inputs`, verified
  with a byte-sum fingerprint per tensor); inside an output tensor → a fresh buffer; inside any other
  device allocation (torch allocator block or `cuMemGetAddressRange`, incl. IPC-mapped peer comm
  buffers) → a copy of that allocation snapshotted after the launch; then the `--in` record's regions
  are written over it. Everything not registered is end-of-launch content, so the agent registers
  what changes during the launch (the docs say: whole scratch at `_in`).
- **Standalone kernel = the candidate's own phase function** behind `#ifdef SS_TASK`, launched
  cooperatively with the same grid (SM count × occupancy) and dynamic smem as declared in
  `SS_TASK_REGISTER`; launched through an `extern "C"` symbol via ctypes, so two variants (two .so
  files) are timed in one process, alternating.
- The only candidate-side host code is `ss_task.py: build_ext(flags) -> .so path` (≈ 5 lines).
- Tolerances: from the case (`atol`, `rtol`, `bf16_rtol`), applied per region as rel-L2 ≤ rtol
  (bf16_rtol for 16-bit floats) and max-abs ≤ atol + rtol·max|golden|; integers exact. Golden is the
  candidate's own capture (not the oracle), so numerically different but valid variants can fail;
  the integrator's `./check_candidate` remains the authority.

   10 extra allocations snapshotted (scratch, 8 comm buffers incl. 7 IPC-mapped peers, rope), 50 MB/rank.
3. In-kernel window of the same phase (full 8-rank NO_PF build with `-DA3_STAMP`, max(end) − min(start)
   over blocks, median of 6 warm launches; launch 21.1–21.4 ms) vs standalone `./task_ab` median (9 reps,
   cold L2), µs:

   | layer | rank | in-kernel | task_ab | diff |
   |---|---|---|---|---|
   | 1 | 0 | 131.6 | 132.1 | +0.4% |
   | 1 | 3 | 115.5 | 115.7 | +0.2% |
   | 1 | 6 | 149.5 | 148.5 | −0.7% |
   | 8 | 0 | 132.9 | 133.1 / 131.3 (2 runs) | +0.2% / −1.2% |
   | 8 | 3 | 115.7 | 122.9 | +6.2% |
   | 8 | 6 | 132.4 | 131.1 / 131.9 | −1.0% / −0.4% |

   All within the 10% target. Correctness: A PASS **bit-exact** on all 3 regions (`hr`, `ucnt`,
   `expert_ids`) for every (layer, rank) tested; inputs regenerated on 1 GPU match the capture's
   per-tensor fingerprints; 176 parameter pointers re-pointed.
4. A/B detects slowdowns: `-DA3_SLOW` (phase twice, counters reset) layer 1 rank 0: B PASS,
   +92.3% → `B SLOWER`; `-DA3_DELAY=10000` (10 µs idle per block, ≈ 8%) layer 8 ranks 0/3/6:
   B PASS, +9.2/+8.4/+8.7% → `B SLOWER` (IQR ≤ 1.4%). A first slow variant that ran the phase twice
   WITHOUT resetting the completion counters was reported `B INCORRECT` (ucnt mismatch) — the
   check catches state the phase leaves behind, not only its main output.
5. `claude -p` (Claude Code 2.1.326, as root in a scratch dir holding only `.claude/agents/engine.md`)
   lists the `engine` subagent with its description and tools. Not yet re-run as an isolated run
   user (the harness isolation was not ready when tested).

6. Final tree re-check (after moving builds out of the lease and adding watchdogs): selftest PASS
   (A 30.7 µs, B 49.2 µs, `B SLOWER +60%`); seed layer 1 ranks 0/7 with `-DA3_DELAY=10000`:
   A/B PASS bit-exact, 131.1 → 141.4 µs, `B SLOWER +7.9%`; 1-GPU lease holds 5–16 s.
   A/A (same tree both sides, layer 8 rank 0): 131.2 vs 131.6 µs, `SAME (within noise)`.

GPU use: ≈ 1.5 min of 8-GPU leases (capture, in-kernel stamps) + ≈ 10 min of 1-GPU leases (per the
lease log, which lost entries across daemon restarts), i.e. ≈ 25 GPU-minutes.

## Lease behaviour
- Both wrappers build OUTSIDE the lease (`--build-only`, no GPU) and then run the GPU part under
  `./gpu_run -g N -m 10`; the builds are cached, so leases hold only the GPU work
  (task_ab ≈ 15–60 s per rank; capture ≈ 1 min on 8 GPUs).
- Python watchdogs: capture exits 124 after `--timeout-s` (480 s; NCCL timeout just below it) and
  skips NCCL/IPC teardown with `os._exit` (an earlier toy capture hung in teardown with world 1);
  task_ab exits 124 after 540 s.
- Capture dirs are large (`rank<r>.pt` ≈ 50 MB + snapshotted allocations per rank for the seed
  setup, ≈ 0.4 GB per capture): the harness should exclude `reports/capture-*` from run snapshots
  / run branches.

## Known limits
- State that lives only in registers / shared memory at a capture point is not captured (e.g. the
  seed's xbar epoch is in a register; its scratch copy is from launch start). Tasks must recompute it
  or the agent must register a buffer holding it. Documented in TASK.d/A3.md.
- Capture adds 2 grid barriers per selected capture point; only the capture build is affected.
- `make_inputs` for one DSv4.1 rank fills most of a B300 (~250 GB); one task_ab replay needs its own
  GPU (it does: 1-GPU lease) and takes ~1-2 min per rank for input generation.
- Standalone timing has cold L2 and no concurrent phases; ratio to the in-kernel window is reported
  by the agent in phases.md (the fixture measured it, below).
- A phase whose code waits on peers (cross-GPU flags) cannot run standalone unless the task skips
  the wait (restored peer buffers already hold the data).
- `--flags-a/--flags-b` need the `=` form (`--flags-b=-DX`).
